# HearPort 传输稳定性协同方案

日期：2026-10-12。状态：设计建议，产品实现和实测尚未完成。

## 1. 目标与边界

在用户实际的 Wi-Fi 场景中，以音乐连续性为主要目标，在用户选择的端到端延迟预算内尽量减少播放缺口、跳过和失真。网络环境作为输入条件，方案在软件层面适应它。

延迟上限由场景选择；100 ms 只用于示例和对照。正常目标延迟应小于上限，为抖动和恢复保留余量。采集、分包、发送等待、传输、接收缓冲、音频处理和输出占用同一份预算。

本次输出为整套设计。后续传输验证继续使用随机数据；音乐时间伸缩和 PLC 的听感需要独立、固定样本的验证。Opus 不进入当前传输实验。

持续可用带宽低于源数据率，或者无数据到达的时间超过现有有效缓冲时，无法同时保证原始内容完整、连续播放和严格有限延迟。软件需要明确选择有限恢复、补偿或同步到更新的源位置；不能把不可恢复的情况隐藏成不断增长的延迟。

## 2. 当前证据与实现

本轮设计依据主工作区代码和 Build 99 两个完整测试会话：

- 房间内：`7c69ea52c99cd05682cd687fbfd2c1c1`。
- 路由器旁：`d5363e95f31afc4225a787c3465528b6`。
- 每处 Datagram 和可靠流各 108,000 个包、300 秒。Datagram 永久缺失分别为 727 和 228；可靠流最终全部到达。
- 房间内最大接收空窗：Datagram 1184 ms、可靠流 167 ms。发送计划延后 P99 约 0.57 ms；iPad 回调后处理最大低于 0.7 ms。
- 上述证据更支持传输阶段等待；尚不能逐项区分射频重试、路由器排队和 QUIC 内部等待。

需要协同修改的现有逻辑：

| 实现 | 当前行为 | 新设计中的约束 |
|---|---|---|
| `DriftController.swift` | 默认最大修正 0.001，使用重采样修正 | 小幅时钟修正与短时缓冲恢复分别估计，统一决定最终源消费速度 |
| `JitterBuffer.swift` | 固定目标包数；运行中超过目标就裁剪 | 目标变成源音频时长；目标以上保留有界恢复区间，最后才跳过 |
| `QuicReceiver.swift` 的 `pumpLocked` | 遇到缺包且已有后续包时可立即生成静音 | 根据实际准备截止时间决定等待、恢复或补偿，避免过早定案 |
| Jitter 与 render ring | 已通过 stagedFrames 尝试合并预算 | 保留合并思想，把处理算法和硬件输出中尚未播放的部分纳入总年龄 |
| 发送应用队列 | 容量 256 包，满时拒绝新包 | 时间期限控制队列内容，容量另作内存约束；保留仍有价值的数据 |
| MsQuic 可靠发送 | 待完成发送上限 128；发送缓存关闭 | 使用源时长、年龄和字节数共同约束，不把完成发送视为已播放 |
| `ReliableAudioLag` | 超过 160 包、连续两次反馈、500 ms 冷却后换代 | 改为与总预算相关的恢复期限；反馈年龄和换代耗时必须计入 |
| 音频诊断的 captured_at | 目前在分包回调附近取时间 | 真实音频应从采集样本位置和采集时钟建立源时间轴 |

容量上限不代表正常情况下填满这些队列，也不能把所有最大容量相加当作已测延迟。

离线变速回放给出的限制：在房间内可靠流、100 ms 初始模型缓冲下，不变速、±2%、±10%、±20% 的迟到包分别为 70、62、42、25，最大模型延迟分别为 100、106.2、125.6、144.4 ms。示例动态 ±10% 为 42 个、120.1 ms；约束最大模型延迟为 100 ms 后为 70 个。该模型按每组最快到达情况对齐，不包含完整基础传输和音频输出延迟，也没有验证音乐音质。

## 3. 方案选择

1. **先完成共用控制，保留可靠流与 Datagram 两种传输进行公平对照。** 时间、预算、缓冲、恢复和诊断共用；不同传输分别决定包修复方式。可靠流作为目前零最终缺包的有效基线。
2. **再验证 Datagram 的限时修复。** 少量 FEC、选择性重传作为候选，在同一预算、同一发送速率约束内评估。当前证据不足以预先宣布它优于可靠流。
3. 同一份音频持续在可靠流和 Datagram 各发一遍会增加负载，未选为默认方案。它也不能消除无线空窗，收益必须足以抵消额外拥塞。

## 4. 统一时间线与预算

每个音频单元表示源样本区间，并关联流/代际、序号、首样本时间和帧数。恒定格式可用流起点加样本位置推导时间；需要扩展协议时只传推导所必需的字段。序号用于识别数据，样本位置用于时间与变速计算。

令 `Lmax` 为用户总延迟上限，`Ltarget` 为当前目标总延迟，`map(tcapture)` 为映射到接收端单调时钟的源采集时间：

```text
目标声学播放时间 = map(tcapture) + Ltarget
最晚声学播放时间 = map(tcapture) + Lmax
最晚准备时间 = 最晚声学播放时间 - 剩余处理与输出时间 - 时钟/调度余量
```

在可控制的范围内，所有等待必须在最晚准备时间前结束。自适应目标改变只能由一个控制器平滑实现；不能在其他模块再次附加等待。源时间连续前进，已播放或已补偿的位置不会因旧包后来到达而倒退。

启动及低频运行时进行双向时间交换，估计偏移与漂移；优先使用较低 RTT 的样本并记录不确定度。往返时间的一半不能证明真实单向延迟，网络非对称、系统输出估计及设备时钟误差需要预留余量。无法建立可靠绝对映射时，区分相对源年龄约束与端到端测量，禁止把日志估计称为声学硬保证。

发送端先以自身时钟执行过期检查，再用接收反馈判断仍可修复的范围。反馈需包含生成时刻、代际及播放进度；使用者检查反馈新鲜度。反馈失效时禁止增加等待或修复负载，接收端仍根据本地期限播放。

准备时间账本包括分包、应用与 QUIC 等待、网络、Jitter、render ring、时间伸缩前视/积压、重采样余量、音频引擎及输出。内存容量与实际延迟分别记录；同一批帧从一个队列移动到另一个队列不产生第二份可用预算。

## 5. 发送节奏、队列与包组织

- 以源时间安排持续发送，控制突发量。核实并保持 MsQuic 默认启用的 pacing；应用侧只约束提交突发和过期数据，不能再放一个等待攒批的独立缓冲。
- 采集回调一次产生多包时，以包年龄、提交期限和剩余预算决定立即提交、短暂平滑或跳过。调度晚了不把全部旧包压缩成一轮无限追赶突发。
- 按最早有价值的截止时间发送；移除过期帧及对应修复任务。原始有效数据与有机会及时完成的修复按紧迫程度调度；无用修复不能挤占新内容。
- 用排队时长、源音频时长及字节数约束应用和传输待处理量。保留硬内存上限，但不以固定包数替代时间预算。
- Datagram 根据可获得的提交/SENT/取消状态限制已受理但尚未发送的积压；不能因为应用队列已经取走数据，就忽略 QUIC 中的等待。已提交数据是否能取消取决于库接口，接收端期限判断始终生效。
- 包长度不得超过当前允许的 Datagram/路径尺寸，避免依赖 IP 分片。可靠流不保证一次应用 StreamSend 对应一个网络包。
- 以音频时长统一包尺寸/频率实验。缩短分包时长增加包率与头部开销；延长分包时长增加等待和单次丢失内容量。变更必须在代际/明确生效位置协商，保持样本时间连续。
- 当前 float32 双声道 48 kHz 有效数据率是 3.072 Mbit/s。相同 968 B 从 400 包/s 降到 200 包/s，不能直接用于保持同样样本格式的完整实时音频。要降低包率，需要同时改变每包时长或数据表示，并重新核算 MTU 与音频质量。

## 6. 接收、自适应缓冲与时钟修正

### 6.1 有效缓冲的定义

分别记录连续可播放源时长、已见数据覆盖区间、待修复缺口、已提交到输出的源区间以及最老待播样本年龄。数据覆盖跨度含缺口，不能当作完整可播放音频；包数量不能直接用于可变包时长或变速后的预算。

启动需达到可播放/可按期限补偿的目标区间；乱序包不能通过只增加总数量而让一个空洞很大的缓冲提前进入播放。

### 6.2 目标缓冲估计

依据未播放决策污染的原始到达信息，估计相对传输延迟、接收空窗和乱序分布，使用滑动/衰减统计及可调尾部分位。目标同时考虑欠载和乱序成本，并在剩余预算内截断。提高目标较快、降低目标较慢，加入死区和保持时间；秒级异常只提高短期风险，不把目标无限抬高。

永久丢包不能通过增加目标恢复。对最终分类未知的包只作当前风险判断，不能使用测试结束后才知道的结果控制在线播放。修复包到达、PLC 或裁剪不得伪装成网络恢复而污染到达统计。

### 6.3 消费速度的统一决策

当前代码的 `maximumCorrection = 0.001` 是项目重采样参数，名义比例为 1 时对应 ±0.1%；它不是 NetEQ 或 LE Audio 规定的上限，也不限制新的缓冲恢复控制。时钟频率偏差、重采样比例和短时源音频消费速度是不同的量。

NetEQ 的 Accelerate/PreemptiveExpand 会按信号相关性进行重叠衔接，缩短或延长音频片段；硬件输出采样率保持正常，源音频时间推进可临时显著快于或慢于输出时间。该方式具有信号条件与触发频率限制，不能等同于持续固定百分比重采样。LE Audio 的 BAP 允许调整名义 SDU 间隔以适应音频时钟偏移与漂移；它未据此指定与 NetEQ 相同的缓冲时间伸缩算法或通用 ±0.1% 修正上限。

长期时钟漂移用稳态样本估计，继续以很小的重采样修正处理。暂态缓冲偏差用保持音高的时间伸缩处理；由统一控制器限制合成后的有效源消费速度、速度变化率、持续时间和样本年龄。

概念上：`缓冲修正量 = 限幅(增益 × 偏差)`，配合死区、平滑和缓慢回归。采用 PI 时必须限制积分，并在缺包、换代、目标变化和限幅时处理积分累积；首个实现优先使用易验证的比例控制。

偏满优先加速恢复；偏空且还有真实有效音频与延迟余量时允许轻微减速。没有数据时由补偿逻辑产生输出，不能继续假定慢放可以创造原始音频。遇到重缓冲、PLC 或跳过，冻结/重置对应估计，避免把网络事故学成时钟漂移。

随机数据模型测试 ±2%、±5%、±10% 及动态幅度，±20% 仅用于观察上界。真实音乐正常幅度、应急幅度及最长持续时间须以音质验证选择；不把大幅线性重采样当作音乐时间伸缩。

目标缓冲以上至硬期限以内为恢复区域，不能一超过目标就裁剪。按当前偏差和允许最大速度计算能否在期限内恢复；恢复不可行或已经过期时才跳过。跳过起点根据剩余预算和最新有效内容选择，不机械回到固定旧目标。

## 7. 缺包决策与有限恢复

同一个源区间只由一个恢复决策负责：

```text
正常接收/已有可恢复数据
    → 预算内等待乱序或修复
    → 到准备截止时间仍缺失：补偿并推进源位置
    → 长空窗或严重过期：衰减、重新同步、有限重缓冲
```

网络线程可以先存储后续包，播放准备不能因为看见后续包就提前把缺口不可逆地补成静音。准备必须留出实际处理前视和输出块时间；已经提交到输出的内容不能等到扬声器播放时才改变。

缺口的实际准备截止时间同时受当前输出需求约束。已有输出缓冲即将耗尽时，需要及时补偿或扩展，不能机械等到总延迟硬上限才生成输出。硬上限限定最长恢复期限，当前输出进度决定音频何时必须准备好。

正常恢复时小偏差变速；期限耗尽时补偿或跳过；持续故障时同步到更新源位置。这些选择由同一个状态决策驱动，避免变速、裁剪、换代和重缓冲同时操作同一段内容。

无网络数据期间输出时间继续推进。重新收到数据时淘汰已过期内容，恢复起点可播放年龄必须满足当前预算。启动和恢复均只执行一次预充填，不能由可靠流换代、Jitter 和 render ring 分别等待一份目标缓冲。

## 8. 两种传输的专用策略

### 8.1 可靠流

沿用现有代际机制。QUIC 管理可靠重传，应用不再为同一可靠音频追加 FEC、重复发送或 NACK 重传。

接收反馈应报告已收到及已播放的源位置、缓冲年龄和生成时间。传输落后与播放落后分开计算，单独最新收到序号不足以证明低延迟。反馈合并、限频且错误代际无效；可以在风险变化时触发一次有界快速更新。

用预算计算恢复期限，替代固定 160 包阈值。把反馈延后、允许处理时间、换代和预充填代价纳入提前判定，不能等预算已经耗尽后再执行两次长间隔确认。保留防振荡判断，但冷却不能延长旧音频的播放寿命。

持续阻塞时取消旧代际、清理未发送旧数据，以更新的源位置启动新代际。接收端拒绝旧代际，统一恢复状态选择预充填和衔接；控制连接保持。新代际仍共享连接拥塞控制，不能宣称换流消除网络拥塞。

短音频段分别放在独立 QUIC 流中可作为后续有条件实验，避免单条流的字节顺序依赖；同一连接仍共享拥塞控制，播放端按源时间排序。须证明它比现有换代策略改善期限内交付，才能承担额外流管理成本。

### 8.2 Datagram

基础路径先完成有界乱序等待与播放决策，再分别测试以下恢复候选：

- **短窗口 FEC：** 原始包即时发出，边发送边形成短窗口冗余。只对缺失范围尝试恢复；窗口恢复时间必须早于所保护内容的准备截止时间。不要为了凑满窗口延迟原始包。
- **选择性限时重传：** 缺口出现后适当等待乱序，再请求；依据剩余期限和保守往返耗时判断是否有机会，起始实验限制至一次。批量、去重请求，过期后取消。
- **有限冗余重复：** 作为最简单的对照方案。重复同一源位置并去重，不独立计入有效音频。相邻副本可能一起遇到突发空窗，间隔仍受期限约束。

FEC、请求重传和重复由同一任务表/决策记录协调。优先使用已经可以恢复的数据；只有已有修复仍不够且期限允许时才安排下一项。结果同时到达只提交一次，播放定案后停止修复。

交织只有在分散短突发损失的收益超过额外重组等待时才值得测试。跨越多个播放期限的长交织块不适合当前目标。

几百毫秒至秒级无线空窗无法由短 FEC 窗口解决。控制器不得在无数据期间无限提高冗余试图填补这种空窗。

## 9. 总负载与拥塞协同

所有原始数据、FEC、重复、重传、反馈及会话内后台传输共用负载预算和 QUIC 拥塞控制。Datagram 不会绕过拥塞控制。参考可持续交付率、排队/RTT 趋势和有机会及时恢复的损失选择冗余，而非只看到缺包率上升就加冗余。

链路余量充足且孤立损失多时，少量修复可能获益；排队延迟持续增长时，限制冗余和过期数据，并暂停/限速非音频批量工作。反馈限频、紧急信号有界，防止反馈风暴。

固定源格式的发送需求低于持续容量是长期稳定的必要条件。只有缓冲和慢放不能解决持续吞吐不足。降低传输表示位宽是独立候选：48 kHz 双声道 PCM24 为 2.304 Mbit/s、PCM16 为 1.536 Mbit/s，有转换与量化质量代价；先随机数据模拟对应负载，真实音频再验证。保持原格式时就明确其最低吞吐需求。

可条件性测试现有库支持的拥塞算法、优先级/DSCP/ECN 等。它们不作为正确性的依赖，且只在库、系统和路径支持时进行单变量对照。避免禁用拥塞控制、无限放大 UDP/QUIC 缓存、激进缩短丢失判定或用大量并行连接争抢带宽。应用优先级不能保证路由器按相同策略处理。

## 10. 音乐恢复与实现开销

真实音频阶段采用低前视、保持双声道一致性的时间伸缩，所有前视和处理耗时从现有预算中扣除。短缺口使用适合音乐的波形/谱预测和衔接，长缺口逐步衰减，恢复时平滑接入；PLC 不承诺复原未知起音瞬态或长时间原始内容。

PLC 对同一源区间只执行一次。补偿输出也必须带源区间信息，最终控制器才可准确计算源进度与有效速度。原始帧、修复帧和补偿帧分别统计。

沿用现有 render ring 与网络/播放边界。重型估计、FEC、日志和可提前完成的音频处理放在播放回调之外；回调只消费已准备输出。后台处理仍须遵守期限，预计算不能形成新的未计费队列。

现有日志未证明应用回调是主要网络空窗原因，故不预先重构全部线程或内存体系。调度优先级、内存复用和日志限量只有出现对应期限违约或回调超时证据时才针对性调整。

## 11. 冲突约束

| 可能冲突 | 必须采用的协同规则 |
|---|---|
| 自适应缓冲提高目标，同时另加重传等待 | 只调整统一播放目标，所有恢复在已有剩余期限内完成 |
| 变速恢复尚未完成，超过目标就裁剪 | 目标以上设置有界恢复区域；硬期限或无法恢复时才跳过 |
| 小幅漂移修正和大幅缓冲修正相互抵消 | 稳态/暂态分开估计，最终有效源速度统一限幅 |
| FEC、重复和 NACK 同时修复同一个缺口 | 一个恢复记录统筹；及时恢复后取消剩余任务 |
| 可靠流重传与应用重传叠加 | 可靠流仅由 QUIC 重传，应用管理过期与代际 |
| 丢包触发冗余增加，冗余又扩大排队 | 总负载预算先决，容量不足时限制冗余与旧数据 |
| 乱序包尚可及时到达，但泵提前补成静音 | 按准备截止时间判断，保留已有输出安全余量 |
| 长期平均正常掩盖一次严重空窗 | 单独考察最长连续缺口、样本年龄和恢复时间 |
| 冷却/反馈延迟导致过期旧音频继续播放 | 接收期限始终生效，冷却只限制频繁重置 |
| 换代、Jitter、render ring 分别预充填 | 一次恢复、一个有效预充填目标 |
| 处理前视与硬件输出未纳入缓冲 | 统一时间账本，按扬声器预计播放时刻约束 |
| 调包尺寸后固定包数阈值语义改变 | 以源样本时长、字节和时间期限计算 |

## 12. 分阶段验证

### A. 时间、预算与离线控制

复用已有两轮日志，比较固定、当前控制、动态速度、自适应目标及完整协同方案。分开改变因素，再组合比较；保持相同源时间线与延迟上限。旧控制模型已能复现当前分析器，新增模型须检查源位置、缓冲空洞、所有输出待播帧以及因果性。

离线控制只能使用当时已收到的消息。不能用未来最快包对齐作为在线时钟方案，也不能把离线消费变化宣称为实测 QUIC 发送排队改善。

### B. 原有环境的随机数据传输

保持当前连接场景，Datagram/可靠流、相同有效源数据率、重复和顺序打乱。每组仍可 30 秒；总计划时长由组数计算。增加源样本位置、准备/模拟播放进度和实际生效控制的必要记录，沿用自动回日志流程。

保留关键阶段的不同含义：计划/采集、提交、API 受理、Datagram SENT 与最终状态、接收回调、处理完成、准备及模拟播放。Datagram 只保存最终状态会失去提交至 SENT 的等待信息；可靠流 SEND_COMPLETE 单独记录，不冒充对端接收或播放确认。真实声学时间需另外测量。

区分只在接收端模拟消费的实验与真正启用反馈、队列期限和可靠流换代的实验；前者主要检查播放模型，后者才观察传输队列是否改善。

### C. 有限恢复候选

优先在可重复的软件注入/回放中验证单个丢失、短突发、长空窗、乱序、重复、反馈变旧及带宽骤降；这些实验与真实网络传输结果分别标记。FEC、一次限时重传和重复分别作对照，再选有效组合，不把所有候选排列成无必要的完整笛卡尔积。

修复数据会改变实际发送负载与拥塞状态，因此离线推演只说明潜力；只有实际传输能证明其净收益。

### D. 音乐验证

使用固定音乐样本覆盖持续音、鼓点、拨弦、复杂混音和静音段，验证时间伸缩、PLC 与衔接的失真及双声道一致性。传输阶段保持随机数据；音频阶段分别测量算法前视、处理和声学延迟。

## 13. 验收指标

在相同延迟上限、源表示及可用负载下比较：

- 期限内原始/修复内容交付率、补偿总源时长、最长连续缺口和恢复时间。
- 真实等待时间、端到端估计/实测延迟分布、上限违约次数、时钟不确定度。
- 接收和发送待处理的源年龄、积压时长、裁剪/跳过及代际次数。
- 变速幅度、连续持续时间、变化次数、时间伸缩累计使用量。
- 实际原始/冗余/重传/控制字节率；CPU、处理截止违约和音频回调欠载。
- 听感/信号失真，独立于传输缺包率报告。

全部到达、没有缓冲欠载、平均延迟更小均不能单独证明音乐更稳定。硬上限方案首先检查预算违约，再比较连续缺口和恢复质量；若收益来自更长延迟、更多字节或有损格式，明确报告该代价。

- [NetEQ Accelerate](https://webrtc.googlesource.com/src/%2B/69a32cc2d397452de9c81375d0b5cc29944e5c4c/modules/audio_coding/neteq/accelerate.cc) 与 [PreemptiveExpand](https://webrtc.googlesource.com/src/%2B/69a32cc2d397452de9c81375d0b5cc29944e5c4c/modules/audio_coding/neteq/preemptive_expand.cc)，信号相关性与重叠衔接实现。
