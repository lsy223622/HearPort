# HearPort 持久连接与限时诊断会话设计

## 目标

让 HearPort 在首次配对后记住最近使用的 Windows 主机，断开后可直接用已保存凭据重连；并提供由 Windows sender 启动的限时调试会话。调试会话结束后，iPad 自动把本次详细诊断记录可靠地传回 Windows，Windows 同时把自身日志保存为本地文件，便于一次测试后关联分析两端问题。

## 当前实现基础

- iOS 已通过 Keychain 保存配对凭据，但主机地址仅保存在 SwiftUI 临时状态中；界面默认认证方式为新配对。
- Windows sender 使用 DPAPI/凭据管理器保存配对凭据；关闭当前连接不会要求删除凭据。
- iOS 已有异步诊断日志、逐秒音频指标和手动导出；音频接收及渲染指标可复用。
- Windows sender 已有逐秒音频汇总。MsQuic 数据报发送状态回调目前只负责释放发送上下文，尚未记入诊断数据。
- 两端通过 `hearport/1` 的双向可靠控制流传递控制帧，音频使用 QUIC DATAGRAM；单条控制消息上限为 65,536 字节。

## 用户行为

### 记住主机并重连

1. iOS 保存最近一次提交连接的主机文本；该文本不是密钥，不写入 Keychain。此功能不改变当前默认端口 52137。
2. 若 Keychain 中存在有效的已记住凭据，启动后默认选择“Remembered”；否则默认选择“Pair new PC”。手动切换认证模式的能力保留。
3. 提供明确的断开操作。断开只取消当前 QUIC/audio session，不删除主机文本或已配对凭据。连接失败也不清除已保存值。
4. 首次配对完成后继续使用现有 Keychain 保存流程；重连仍执行已记住认证和 Windows 证书身份校验，不弱化认证。

### 限时调试会话

1. Windows sender 增加可选参数 `--debug-seconds=N`；省略时完全保持普通串流行为。有效时长为 60 至 600 秒，推荐值为 300 秒。
2. 调试参数生效时，sender 只接受声明支持诊断上传的接收端。未声明能力的旧版 iPad 不开始这次限时测试，并在 Windows 日志中给出升级提示；普通模式继续兼容已有接收端。
3. 已认证并成功开始音频流后，Windows 建立诊断会话 ID 并发送诊断开始控制消息。iPad 从收到开始消息起记录本次会话的逐包事件和音频实时指标。
4. 时长到期后，Windows 停止本次音频流并发送结束原因；QUIC 连接保持可用，等待诊断报告上传完成。结束不会操作 Windows 播放器或暂停系统音源，只停止 HearPort 本次发送。
5. iPad 定稿本次报告，按固定大小分块通过现有可靠双向控制流上传。Windows 校验会话 ID、块序号和总长度，边收边写入磁盘；完整落盘后返回应用层确认。iPad 收到确认后删除待传文件。
6. 若串流或上传期间连接意外断开，iPad 定稿并保留一个有界的待传报告；下次连接到支持上传的 sender 后自动先补传。上传未获确认时不得删除。上传完成后才允许该 sender 开始下一次调试采集。

## 诊断数据与实时性能

### Windows

- 现有服务/QUIC 诊断继续输出到控制台，同时实时写入与 sender 可执行文件同目录的 `HearPort-sender.log`；每次进程启动创建本次日志并打印完整路径。诊断通过独立写入线程落盘，文件不可用时在控制台报告原因，sender 保持既有运行行为。配对 PIN 仍只显示在交互控制台，不写入日志文件；不得把整个 stdout/stderr 无差别重定向到日志。
- 调试会话另记录按音频 stream ID 和序号关联的紧凑事件：采集/规范化/packetize、入队和出队、队列深度及高水位、DatagramSend 接受/失败、数据报最终状态、最大数据报长度和采集格式。
- MsQuic 状态只记录当前链接版本实际提供的状态。它们描述传输层，不代表 iPad 音频线程已消费或播放该包。

### iPad

- 记录数据报序号和本机单调时钟到达时间、解码与接收结果、缺口/重复/迟到、缓冲入队/出队及裁剪/补偿、drift/resampler 状态。
- 保留现有逐秒原子指标，并记录渲染欠载、音频路由/采样率变化、音频 session 中断与恢复、后台/前台生命周期等事件。
- 报告带有 app/build、设备/OS、buffer 配置、会话 ID、stream ID、开始/结束原因及事件计数；不包含音频 PCM、PIN、pair secret、认证消息或 TLS 私钥。

### 非阻塞约束与边界

- 逐包记录仅在调试会话启用，写入预分配且容量固定的记录缓冲区；队列满时不等待，增加明确的 trace-drop 计数。容量至少覆盖 600 秒、每秒 400 个音频数据包的逐包记录；超出部分由 drop 计数明确指出。
- 音频 capture/render 实时回调只更新现有原子计数或提交固定字段，不做字符串格式化、文件 I/O、压缩或网络传输。Windows 的现有文本日志文件由独立诊断写入线程处理；控制台/文件写入失败不得阻塞媒体工作线程。
- 结束后在非实时线程序列化并传输报告。报告使用带格式版本的 UTF-8 行式记录，分块大小不超过 60 KiB，遵守现有控制帧上限。
- 两端使用各自单调时钟并用 session/stream/packet ID 关联；报告不声称未校准时钟下的精确单向网络延迟。
- Windows 保存目录为 sender 可执行文件同目录下的 `HearPort-diagnostics/<session-id>/`，包含 Windows 会话 trace、iPad 上传的会话报告及 manifest。Windows 先写入临时文件；收到完整、顺序正确且字节数匹配的报告后再原子完成该会话目录并确认。相同 session ID 已完成时重复上传只重新确认，不覆盖完整报告；断线后重传从第 0 块开始并重建未完成临时文件。普通持续日志仍在 `HearPort-sender.log`。

## 协议兼容

- 保持 ALPN `hearport/1`。现有普通控制流程在诊断关闭时不改变。
- 在 ConnectRequest/SessionReady 中增加可选能力字段；旧实现忽略嵌套的未知字段，因此新 iPad 可以连接旧 sender。旧 iPad 不声明上传能力，新 sender 在调试模式下不启动限时测试。
- 为诊断开始/结束、报告开始/分块/完成和接收确认定义新的控制消息。报告分块通过既有可靠控制流顺序传送；每块带 session ID 和递增索引，报告头声明总块数/总字节数。接收端仅在所有块完整写入后确认。
- 新 iPad 连到不支持诊断上传的旧 sender 时，正常认证和普通播放保持可用；若存在待传报告则保留，直到连到支持的 sender。

## 验收标准

1. 新安装首次无凭据时仍进入配对模式；成功配对后重启 app，主机仍在且默认认证为 Remembered。
2. 用户断开并重连时不需要 PIN；Pair new PC 仍可手动选择；断开不会删除 Keychain 凭据。
3. 普通 sender 命令不触发诊断协议或包级追踪，既有普通播放兼容性保持。
4. `--debug-seconds=300` 在音频流开始后采集 300 秒，到时停止 HearPort 音频并等待报告确认；Windows 产物同时能关联到 iPad 报告和 sender 逐包 trace。
5. 序号、发送/接收单调时间和接收处置可用于区分发送端未接受、传输层丢失/确认、接收端缺包/乱序，以及接收后缓冲或渲染造成的断续；不把传输 ACK 当作播放确认。
6. 中断连接会保留部分 iPad 报告；后续连接上传确认后本地待传报告删除，未确认时保留。
7. 上传的块丢失、乱序、重复、长度不符或 Windows 写入失败均不得产生成功确认或删除 iPad 报告。
8. 在模拟高频事件和缓冲满的测试中，capture/render 实时回调不执行文件或网络 I/O、不等待写线程；缓冲溢出可从报告中的计数识别。
9. Windows 普通及调试会话的非敏感服务/QUIC 诊断出现在 `HearPort-sender.log`；日志路径可直接由启动输出得知，配对 PIN 不出现在日志文件中。

## 不在本次范围内

- 实时上传日志、录制/上传音频内容、分析或上传用户媒体。
- 未经时钟同步推导单向网络延迟。
- 新的配对算法、凭据格式或 TLS 信任规则。
- 可视化播放曲线、自动定位根因或对每个可能故障作出保证。
