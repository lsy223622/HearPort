# USB 与网络并行发现、USB 优先连接

日期：2026-10-17

状态：用户已于 2026-10-17 确认，按 USB 转发已有加密 QUIC 数据包的方式实施

## 目标与范围

把已经验证可用的 usbmux 链路接入现有 Windows 与 iPad 程序。用户开启连接后，两种路径同时可用，USB 优先；同一时刻只有一条音频链路。正式程序自行完成发现和连接，不依赖 Python 探针。

沿用主工作区。复用现有证书、PIN 配对、记住设备、音频处理和诊断机制。USB 首次配对不要求先连接 Wi-Fi。首次接入 Windows 仍可能需要 Apple 的设备支持服务、解锁 iPad 和系统“信任此电脑”操作。

“两端扫描”按平台能力实现：Windows 同时发布网络服务、接收网络连接并发现 USB 设备；iPad 同时浏览网络服务、监听 USB 入口。iPad 不需要也不能依靠普通应用枚举 Windows 的 USB 设备。

## 已确认的基础

- 现有 USB 探针在真实 iPad 上完成 180 秒、约 3.17 Mbit/s 的双向测试，应用层计数一致，未发现序号缺失或校验错误。
- 这只证明前台链路可用，不是正式音频、锁屏或端到端播放延迟的验证。
- 正式网络路径为 iPad QUIC 客户端连接 Windows MsQuic 服务端；TLS 证书绑定和应用配对都依赖这一方向。
- 当前没有完整的网络自动发现，主要依赖手动地址；需要补充 DNS-SD 发布与浏览，保留手动地址入口。
- 现有服务端只追踪一个连接、一个认证状态，不能直接让两个连接共用这些状态。

## 传输方案比较

| 方案 | 优点 | 代价与限制 |
| --- | --- | --- |
| USB 转发加密 QUIC 数据包（推荐） | 保持现有 TLS、配对与音频协议；可直接复用网络路径的播放和诊断 | 多一层本机 UDP 转发；QUIC 位于可靠 TCP 流上，存在重复可靠性与阻塞成本，必须实测 |
| 新建原生 USB 音频流及安全连接 | 可以减少协议层，直接控制流队列 | TCP 发起方向与现有 TLS 角色相反；需要新的安全传输适配、认证衔接及音频发送实现，改动明显更大 |

首版选择第一种。桥接保留每个 QUIC 数据包的边界，承载的始终是原有 QUIC 数据包，不向 USB 明文发送音频或配对凭据。USB 的底层可靠传输不会因上层选择 Datagram 而变成不可靠传输；界面和日志区分物理路径与音频协议模式。

这是一项复用现有安全和播放路径的工程选择。是否需要原生 USB 协议，应由正式播放中测得的转发开销和阻塞情况决定。

## 数据流

```text
iPad 原有 QUIC 客户端
    ↕ 本机 UDP
iPad USB 桥接器（TCP 监听，仅 127.0.0.1:52138）
    ↕ 带长度的数据包，经 usbmux / USB
Windows USB 桥接器
    ↕ 本机 UDP
Windows USB 专用 MsQuic 入口（仅 loopback）
    ↕ 原有认证、控制与音频协议
Windows 单一音频会话

iPad 网络 QUIC 客户端 ↔ 局域网 ↔ Windows 网络 MsQuic 入口
```

Windows USB 入口与网络入口分开，桥接器只能转发至本程序创建的固定本机端点；不提供任意地址代理。USB 外层协议只承担版本和数据包边界，长度上限 65,535 字节，异常版本、零长度、越界或中途 EOF 均关闭该通道。解析必须支持拆包和连续多包，读写均可取消。

Windows 使用原生 C++ 连接本机 Apple 设备服务，只选择 `ConnectionType=USB`，不把 Apple 的网络设备发现当作 USB。发现多个设备时逐个检查 HearPort 入口，候选数量有界；只有通过 HearPort 认证的设备才能成为活动会话。

## 发现与认证

- Windows 使用系统 DNS-SD API 发布 `_hearport._udp` 和实际 QUIC 端口，iPad 使用 `NWBrowser` 浏览；服务实例名、地址和 TXT 字段都不作为身份凭证。
- Windows 监听 Apple 设备接入/移除事件，并在设备服务恢复或 app 尚未启动时有界退避重试。缺少 Apple 服务时网络继续工作，界面显示 USB 不可用原因。
- iPad app 启动后准备本机 USB 入口及网络浏览。是否发起认证仍遵守连接按钮和既有自动连接设置，发现设备不等于允许播放。
- 两条路径使用同一 Windows 证书身份和已存储的配对凭据。USB 的 loopback 地址不得覆盖记住的网络地址，也不得成为配对身份。
- 已信任电脑可以自动恢复连接。陌生设备仍需要用户打开配对窗口并输入 PIN；不自动更换记住的电脑。
- 两个入口的候选连接各自维护解码器、认证进度和关闭状态；共享凭据存储与配对窗口访问串行化。候选通过认证前不启动采集或播放，不打断活动会话。

## USB 优先与切换规则

连接协调器串行处理发现、认证和关闭事件，并使用连接代号隔离迟到回调。

| 当前状态 / 事件 | 行为 |
| --- | --- |
| 用户点击连接 | 同时准备网络与 USB；已有可用 USB 时先尝试 USB，否则先连网络，继续发现 USB |
| 网络播放期间，USB 候选通过同一设备认证 | 结束旧音频流、清空旧播放与时钟状态，再用新流启动 USB；切换有短暂停顿 |
| USB 播放期间发现网络 | 记录网络可用，不启动第二路播放 |
| USB 拔线或通道失效 | 立即结束 USB 流，重新认证已知网络端点并恢复播放；同时等待 USB 恢复 |
| USB 候选认证失败 | 关闭候选，保留当前网络播放；失败原因可见，并退避重试 |
| USB 插拔反复抖动 | 每次只维护一个切换事务；失败后退避，避免持续抢占网络 |
| 用户手动断开、电脑端停止或退出 | 停止自动连接意图；本次停止不触发另一路自动续播 |
| 正常测试结束、报告回收完成 | 保留完成状态，不自动开始普通音频播放 |

旧连接的关闭回调不得停止新连接的采集、清空新认证、覆盖新 UI 状态。新链路必须重新测量时钟并建立流，不沿用网络路径的时钟映射或未播放队列。

本版采用重新建流的切换，不承诺无缝连续播放；USB 插入和拔出都必须给出准确的状态提示。

## 队列与延迟

- 保留现有音频截止时间与发送窗口；桥接不新增播放缓冲目标，不把 USB 转发预算加到用户总延迟预算之外。
- 两端异步转发，有界队列、发送完成反馈和可取消等待。每方向桥接待发字节上限 64 KiB；同时记录队列最老数据的等待时间。到达当前会话最大延迟预算或超过容量时关闭失效通道，不能继续增长队列或截断正在写入的帧。
- 缺少有效播放预算时只允许有界的握手阶段，采用现有连接超时；不无限缓存待认证流量。
- 该保护只能限制应用层桥接队列，不能保证操作系统和 usbmux 内部没有积压。诊断必须同时记录实际截止时间失约与断连，不能把队列清空造成的断音隐藏为低延迟。
- 首次接入保留用户现有播放预算和逻辑音频模式。正式 USB 播放验证后才能决定更低的默认预算，不用探针 RTT 直接替代端到端预算。

## 界面与现有测试

两端连接区显示“正在寻找设备”“网络连接”“USB 连接”“正在切换到 USB”“USB 已断开，正在连接网络”等状态，以及 USB 不可用的可操作原因。继续遵循现有控件样式，不增加独立 USB 测试 app 的操作步骤。

网络测试与环境校准明确绑定网络路径，运行期间不因 USB 接入切换路径。音乐测试在开始时确定物理路径并保持至报告回收；拔线或连接失效时标记中断，不把两种路径拼为同一条有效结果。普通播放持续执行 USB 优先策略。两端显示相同的活动路径，报告写入物理路径和连接代号。

## 验证与交付

集中完成开发后做一轮相关验证：

1. Windows 原生 usbmux 请求/响应、USB 过滤、数据包分帧、畸形输入、取消与断线的聚焦测试。
2. 协调器状态测试：网络先到、USB 先到、候选认证失败、USB 插拔、旧回调迟到、用户停止、测试正常结束及重连退避。验证始终只有一个活动音频流。
3. 本机桥接回环验证双向 QUIC、原有配对与记住设备认证、队列背压及关闭，不只测外层字节回声。
4. Windows 构建与相关回归；GitHub Actions 执行 Swift 测试和正式 iPad app 构建。
5. 用户安装后集中验证实际 USB 音频、首次 USB 配对、网络到 USB / USB 到网络切换及锁屏。实机结果与构建通过分别报告。

音频文件、设备原始标识及原始日志留在本地，不提交到公开仓库。
